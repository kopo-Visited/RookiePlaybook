# PR 가이드

## PR 생성 규칙

- PR은 반드시 이슈와 연결한다 (본문에 `closes #이슈번호`)
- 하나의 PR = 하나의 기능/수정. 여러 기능 몰아넣기 금지
- **Draft PR 활용**: 작업 중 미리 공유하고 싶으면 Draft로 올린다

> **Draft PR이란?**
> "아직 완성 안 됐지만 진행 상황을 공유하거나 방향에 대해 피드백 받고 싶을 때" 올리는 PR이다.
> - 일반 PR과 달리 merge 버튼이 비활성화되어 실수로 merge되는 사고를 방지한다
> - 리뷰어는 강제로 리뷰할 의무가 없고, 작업 완료 후 "Ready for Review" 버튼을 누르면 일반 PR로 전환된다
> - **만드는 방법**: GitHub에서 PR 생성 시 "Create Pull Request" 버튼 옆 드롭다운 → **"Create Draft Pull Request"** 선택

## PR 제목

커밋 컨벤션과 동일한 형식 (기능ID 포함):

```
feat(be): 라쿠텐 상품 조회 API 구현 (F-003)
```

Squash merge 시 이 제목이 develop의 커밋 메시지가 되므로 신경 써서 작성한다.

## PR 본문 (템플릿)

`.github/PULL_REQUEST_TEMPLATE.md` 의 템플릿을 따른다.

## 리뷰 규칙

- **승인 인원은 대상 브랜치에 따라 다름** (브랜치 보호로 강제): `develop` 2명, `main` 3명(작성자 제외 전원), `main` hotfix는 2명. 상세는 [branch-strategy.md](./branch-strategy.md) 참조
- self-merge 금지 (본인 승인으로 본인 PR merge 불가)
- 리뷰 요청 받으면 **24시간 이내** 리뷰 (주말 제외)
- 리뷰는 코드에 대한 것이지 사람에 대한 것이 아니다

## 리뷰 코멘트 컨벤션

| 접두어 | 의미 |
|--------|------|
| `[필수]` | 반영해야 승인 |
| `[제안]` | 반영 여부는 작성자 판단 |
| `[질문]` | 의도 확인 |
| `[칭찬]` | 좋은 부분 언급 |
| `[승인]` | 전체적으로 문제 없음. GitHub 승인 버튼과 함께 사용 |

예시:
```
[필수] null 체크 없이 접근하고 있어서 NPE 가능성 있음
[제안] 이 부분 stream으로 바꾸면 더 읽기 쉬울 것 같아요
[승인] 전반적으로 깔끔하게 구현됐습니다 👍
```

## Merge 규칙

- CI(린트 + 빌드 + 테스트) 통과 필수
- 충돌 해결은 PR 작성자가 한다
- merge 후 브랜치는 **원격, 로컬 모두 삭제**한다
  - 원격: merge 완료 후 GitHub에서 표시되는 "Delete branch" 버튼 클릭
  - 로컬: `git branch -d feature/F-001-login` (merge 완료된 브랜치는 `-d`로 안전하게 삭제)
